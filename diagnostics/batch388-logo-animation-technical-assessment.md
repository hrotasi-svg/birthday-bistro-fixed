# 門店選擇頁 Logo 動畫：圖層、載入與跨裝置技術判斷

## 結論摘要

在Logo動畫尚持續調整時，應**保留完整分層版本作為唯一可編輯母檔**，而不是先把所有層合併。合併不是目前延遲或跨裝置位置差異的主要解法；它會犧牲火焰色彩、單獨時窗、透明鍵控與後續定位調整能力。若日後動畫經使用者明確定稿，可額外產生一個已最佳化的播放衍生檔，供效能測試，但不得取代可回復的分層母檔。

| 使用者問題 | 技術判斷 | 建議 |
| --- | --- | --- |
| a. 合併或保留圖層？ | 應保留分層母檔。火焰、煙霧、水面、蝴蝶與色相同步各有獨立時間窗和透明規則。 | 定稿前維持分層；定稿後才額外建立最佳化衍生播放檔。 |
| b. 合併是否改善開站延遲？ | 可能略降少量DOM／合成負荷，但不保證改善首開延遲；大型合併影片也需下載與解碼。 | 先量測網路、解碼與主執行緒，再決定是否製作衍生檔。 |
| c. 是否先下載完整分層檔再合併？ | 是。可編輯分層素材與播放最佳化檔應分開保存。 | 備份完整分層母檔；只從已驗收的母檔產生衍生檔。 |
| d. 如何改善開站延遲？ | 先讓首屏只載入背景、Logo與真實火焰；非首屏的煙霧、水面、金幣及熄火媒體延後至其顯示窗口前。 | 需要另立效能批次與實機量測後才修改預載策略。 |
| e. 為何桌機／iPad／App會有位置或尺寸差？ | 主要不是圖層數量，而是iOS/iPad使用不同的火焰來源、裁切與裝置像素比例／WebView合成差異。 | 把所有顯示層以同一個標準化火焰錨點校正；各裝置分別量測，不以合併圖層取代校正。 |

## 目前程式的可驗證原因

真實火焰在一般裝置使用WebM，在iPad／iPhone與觸控Mac使用不同MP4相容來源；兩者再經固定裁切、輸出比例、X／Y位移與每影格的Canvas透明鍵控處理。因此不同裝置可產生不同的可見火焰邊界，即使外層CSS位置相同。這是位置與尺寸誤差的主要技術風險，而非單純圖層數量。

此外，真實火焰每一影格都會從影片畫面繪入Canvas、讀取像素、做透明鍵控後再輸出；同頁又有多個原生GIF／MP4覆蓋層。合併所有圖層會移除部分合成節點，卻也會把可調整的獨立時序、色相、透明鍵控與無障礙減少動態效果能力一併固定在單一媒體中，且可能導致較大的單一媒體首載入與解碼成本。

目前正式站已對SPA HTML採取不快取策略、對內容雜湊靜態資源保留可快取策略，因此「載入到舊版」不是HTML長期快取的預設結果。首開延遲較可能來自媒體下載、瀏覽器解碼、Canvas逐影格處理以及多個覆蓋層在第一個循環啟動時的工作量。

> 建議的後續順序是：先讓使用者正式驗收目前動畫；再另開一個**只做效能量測與預載策略**的批次。該批次應先在桌機、iPad與手機實測首屏時間、第一個動畫循環與記憶體／掉幀情況，再決定是否建立不取代母檔的最佳化衍生動畫。
